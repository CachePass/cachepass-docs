# CachePass Architecture

## 1. Independent repositories

```
CachePass/                  workspace folder — NOT a repository
├── cachepass-website/      git repo · SvelteKit static marketing site
├── cachepass-webapp/       git repo · SvelteKit SPA + Rust→WASM crypto engine
├── cachepass-backend/      git repo · Rust/Axum API, migrations, Docker Compose
├── cachepass-docs/         git repo · these design documents + contributor instructions
└── docs → cachepass-docs/docs   (symlink, as are README.md, CLAUDE.md, .claude)
```

| Repository | Owns | Builds with | Depends on others? |
|---|---|---|---|
| `cachepass-website` | Public product site, SEO, self-hosting overview | Bun | No |
| `cachepass-webapp` | Auth UI, vault UI, **all vault cryptography** (`crypto/` Rust crate → WASM), API client, password generator, TOTP | Bun (Rust only to regenerate WASM) | No — talks to the backend only over HTTP at runtime |
| `cachepass-docs` | Design documents (this folder), project-wide `CLAUDE.md` and `.claude/` rules | — | No |
| `cachepass-backend` | HTTP API, PostgreSQL schema, auth/sessions, encrypted blob storage, OpenAPI document, deployment (Dockerfile, Compose, Caddy) | Cargo, Docker | No — the Compose file references the webapp as a container image |

No code, packages or Cargo workspaces are shared. Contracts are shared as
documents:

- **API contract:** `cachepass-backend/openapi.json`, generated by Utoipa from
  the code (`cargo run -- openapi`), checked by a test that fails when the file
  is stale. The webapp mirrors it in `src/lib/api/` with Zod schemas.
- **Crypto contract:** [CRYPTOGRAPHY.md](CRYPTOGRAPHY.md). The webapp
  implements it; the backend validates only the envelope structure, in its own
  `crates/cachepass-envelope` crate. Both test against the same vectors.

## 2. Runtime topology

```
Internet
   │ HTTPS (443)
   ▼
Caddy reverse proxy (TLS, HSTS)                      backend repo: deploy/Caddyfile
   ├── /api/*  ──────────► cachepass-api :8080       backend repo: Dockerfile
   │                         │ internal network only
   │                         ▼
   │                       PostgreSQL :5432 (volume: pgdata, never published)
   └── /*      ──────────► cachepass-webapp :8080    webapp repo: Dockerfile (static files + CSP)
```

The webapp and API share **one origin** (`https://vault.example.com` and
`https://vault.example.com/api`). This keeps cookies `SameSite=Strict` and
`__Host-` prefixed, and removes the need for CORS in the default deployment.
Strict CORS (explicit allow-list, credentials) is supported for split-origin
setups via `CACHEPASS_ALLOWED_ORIGINS`.

The marketing website is deployed separately (any static host) and only links
to the webapp.

## 3. Request flow examples

### Registration
1. Webapp: user enters email, account password and master password (must differ).
2. WASM: generate vault id, salt and DEK → derive KEK (Argon2id + HKDF) → wrap DEK.
3. `POST /api/v1/auth/register {email, password, vault_id, key_envelope}`.
4. API: validate, hash the account password (Argon2id), and in one
   transaction insert the user, the vault and the email verification token.
   Send the verification email. Response is identical for existing emails.

### Login → unlock → sync
1. `POST /auth/login {email, password}` → session cookie (or an MFA challenge,
   then `POST /auth/login/mfa`).
2. `GET /vault/key-envelope` → WASM derives the KEK and unwraps the DEK locally.
3. `GET /vault/sync` → all item/folder ciphertexts plus the vault revision;
   decrypted in WASM, held in memory.
4. Subsequent `GET /vault/sync?since=<revision>` returns only changes and
   tombstones.

### Item update (optimistic concurrency)
1. WASM encrypts the full item payload (AAD = vault id + item id).
2. `PUT /vault/items/{id} {revision: n, ciphertext}`.
3. API: `UPDATE … WHERE id = $1 AND vault_id = <session vault> AND revision = n`.
   No row → 404 (not yours or missing) or 409 `revision_conflict` with the
   current revision. The webapp re-syncs and asks the user to retry.

## 4. Backend structure (modular monolith)

```
src/
├── main.rs            CLI: serve | migrate | openapi | healthcheck
├── lib.rs             build_app(): router + middleware stack
├── config/            env-based configuration, validated at startup
├── errors/            AppError → uniform JSON error envelope
├── routes/            /api/v1 router assembly + OpenAPI document
├── middleware/        security headers, CSRF, rate limiting, client IP, auth extractor
├── application/       AppState, mailer abstraction, background maintenance
├── domain/            value types: Email, Password policy, Revision, EncryptedBlob
├── infrastructure/    database pool, password hashing, tokens, secret box, SMTP
└── modules/           auth · users/account · vault · folders · sessions · devices · audit
                       each: handlers (thin) → service (rules) → repository (SQL)
crates/cachepass-envelope/   pure envelope/KDF-parameter validation (no I/O)
```

## 5. Webapp structure

```
crypto/                Rust crate → WASM (spec implementation)
src/lib/
├── crypto/            WASM loader, typed engine wrapper, base64url, payload codecs
├── api/               fetch client (CSRF, errors) + Zod schemas mirroring openapi.json
├── features/          authentication · vault · folders · generator · security · settings
├── components/        ui/ (shadcn-svelte) · layout/ · vault/ · auth/ · shared/
├── stores/            session + vault state (Svelte 5 runes, memory only)
├── schemas/           item payload schemas (Zod)
└── utils/
src/routes/
├── (auth)/            login · register · verify-email · forgot-password · reset-password · unlock
└── (app)/             vault · favorites · folders · generator · security · settings
```

The webapp is a static SPA (`adapter-static`, SSR disabled): there is no
Node server holding secrets, and the CSP covers every page.

## 6. Data model (summary)

See `cachepass-backend/migrations/` for the authoritative schema.

| Table | Purpose | Sensitive content |
|---|---|---|
| `users` | Account, Argon2id password hash, verification state | hash only |
| `vaults` | One per user; revision counter; KDF params + wrapped key | ciphertext only |
| `vault_items` | Item ciphertext, revision, soft-delete timestamp | ciphertext only |
| `folders` | Folder-name ciphertext, revision | ciphertext only |
| `vault_tombstones` | Permanently deleted ids for incremental sync | ids only |
| `sessions` | Hashed session tokens, expiry, device link | hashes |
| `devices` | Browser/device records (label, user agent, last seen) | metadata |
| `email_verification_tokens`, `password_reset_tokens` | Hashed, expiring, single-use | hashes |
| `mfa_methods` | TOTP secret (server-key encrypted), recovery code hashes | encrypted / hashed |
| `audit_logs` | Security events per user | metadata |

Item type, name, folder assignment and favourite flag are **inside** the item
ciphertext. The server cannot filter or search them, by design.
